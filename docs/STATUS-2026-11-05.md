# Infinite Future Bank — Platform Status (5 November 2026, updated end of day)

What works, what doesn't, what to fix now, and what to fix later.

**How this was checked:** a read-only audit of the **live** Supabase project
(`nfztdpyygfrpbjbhidxe`, "IFB", production): its tables, security settings, database
functions, storage buckets, deployed edge functions and configured secret *names*.
No customer records were read. It was cross-checked against the code on `main`
and against tests run from outside, as an anonymous visitor.

## 3. What doesn't work, or works but is unsafe

### 3a. Works, but unsafe (old server code still live: Phase 2)

| Function | Problem | Gateway login check |
|---|---|---|
| `process-withdrawal` | Withdraws **anyone's** balance to an attacker's bank | ❌ off |
| `process-payout` | Same as above, for payouts | ❌ off |
| `ifb-charge-card` | A negative amount moves money from a merchant to the attacker | ❌ off |
| `verify-otp`, `face-auth` | Account takeover (demo OTP bypass; face login by email only) | — |
| `kyc-*` admin functions | The admin login token can be forged | ❌ off |
| `send-email` | Anyone can send email as IFB | — |
| `flutterwave-transfer` | Pays the dollar amount as local currency (for example $10 becomes 10 cedi) | — |
| `confirm-deposit`, `stripe-webhook` | A deposit can be credited twice | — |
| `issue-ifb-card`, `link-external-card`, `process-afr-transfer`, `process-p2p-receipt`, `afr-mint` | Trust the user id or amount sent by the caller | — |

The fixed versions are on `main`. Deploying them changes behaviour for the **old**
app version, so they go live after the new app reaches Production (section 5).

### 3b. Not working

| Item | Problem |
|---|---|
| **Withdrawals: bank (ACH/SWIFT), card payout, P2P, cash pickup** | Since a change on 27 October, every withdrawal **shows an error** ("…catch is not a function") right after the money is locked in escrow. The order exists and the money is in escrow, but the app crashes before it sends the processor's in-app notification (a database trigger may still alert them, if its server key is set up). The user thinks it failed and may try again, locking more money. **Cause:** the app called `.catch()` on a Supabase database call, which the Supabase library doesn't support, so it crashed. **Fix:** in code (`WithdrawalPage.jsx`); ships in 1.5.9. |
| Withdrawal fee (0.5%) | Shown to the user, but **never charged**: the charge was taken out of the app on 27 October and nothing on the server replaced it. It should be charged inside `process_p2p_escrow` (X8). |
| IFB Audit purchase | Same `.catch()` crash as withdrawals: the purchase fails after the history line is written. Needs a careful fix, because it also involves charging the user (X9). |
| Pay Bills | Takes money from the wallet, but no biller integration exists (marked *Coming soon* in 1.5.8). |
| Invoicing | Its links point to an address that doesn't exist (marked *Coming soon*). |
| Clyrix Health, Praxci Edu, AI Team, Emergency SOS | Simulated with timers, with no real backend (marked *Coming soon*). |
| Lending, P2P Escrow, Smart Contracts, Venture Exchange, Listings, Wealth, Insurance, Pension, AgriShield, AFR Node | Need a licence (marked *Licence pending*). |
| Mobile-money withdrawals | Off in the new code until currency conversion is built. The **old** live code still pays the wrong amounts. |
| `kyc.infinitefuturebank.org` | No DNS record, so the site is unreachable. |

The badges and gating ship in app **1.5.8**. The old app version and the old web
build still show these features as if they work.

**Users who saw the withdrawal error:** their withdrawal isn't lost. The order
shows under *History* in the withdrawal screen, and the processor can complete it
(processors may need to check their open orders, since the in-app alert may not
have been sent). Support should look for users with **more than one** escrowed withdrawal order since
27 October; they probably retried after the error. An extra order can be cancelled
to release that money.
